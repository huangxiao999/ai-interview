## 3. 清理协议及本轮修复

1. 用户删除：复核当前凭证代次、权限、预期账号及根资格；屏障、唯一请求、全部当前清理意图与数据库正文清理共同提交。清单写失败时全部回滚，不能先禁访再丢失处理意图。
2. 文件清理在业务事务外执行。每个目标先持久记录 `cleanup_attempted_at`，再删除真实文件；完成登记事务共同更新上传、清理项及删除请求。
3. 文件故障持久记录 `cleanup_error_code=FILE_IO`；下轮重试持续禁访。文件已删但登记事务失败时仍保留未完成项，下次重复删除缺失文件安全，随后登记完成。
4. 队列按 `cleanup_attempted_at NULLS FIRST,id` 选取既有最多 100 项。原查询没有进度顺序，固定故障批次可能反复占据窗口；本轮补轮转，优先未尝试或最久未尝试项。此风险来自结构核查，未宣称在旧实现上完成运行复现；101 条夹具只验证既有 100 项选取边界，不新增产品容量或压力指标。
5. 清理放在接收对账/解析调度之前，后者故障不阻止该轮先执行清理。应用重启从原状态与清单续做；仍以单活动应用执行者、同一受控私有根为前提。
6. `UploadService.auditCleanupDeadline` 每 60 秒核查原 `cleanup_deadline_at`，超期发不含正文的数量告警；只读 SQL 输出请求期限及未完成项。此为技术巡检频率，不改 24 小时业务期限，不重置受理时间、不伪报 `CLEANED`。实际超期属于验收违约，不能用“仍在重试”免责。

V6 仅向 `material_upload` 增加两个字段和部分索引，不新增表，不修改 V1～V5。V1～V6 均由 Flyway 管理，Session/SQL 自动建表仍关闭。

## 5. 场景、事件顺序和独立预期

下列断言使用真实 PG/文件/HTTP；仓储专项直接调用生产仓储，不用替身。浏览器是通过本机 Chrome 和真实应用执行，网络故障由测试拦截层控制。
