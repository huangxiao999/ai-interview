## 2. 本次实际行为

- 直接进入 `/app` 时先核实 `me`。明确 401 转登录；查询失败显示“暂时无法核实”，遮蔽工作区身份并提供重试。没有把查询失败当作匿名或登录成功。
- 登录名在前端按原值检查 3～64 位 ASCII 字母、数字、`.`、`_`、`-`；不 `trim` 或改大小写。后端仍独立校验。空密码拒绝提交，错误凭证统一显示“账号或密码不正确”，不提示账号是否存在。
- 登录前获取 CSRF；登录成功后查 `me` 确认身份并刷新 CSRF。退出使用 POST 和当前 CSRF；成功后清除身份、跳转登录。密码及 CSRF 只留在当前页面/内存，离开登录页清空密码。
- 提交中禁用重复操作。写请求响应丢失或服务错误时先核实 `me`，不自动再次提交；仍无法核实则保留未知状态。完整的丢包、多窗口与旧响应竞态属于 DT-06。
- 工作区只显示当前账号和功能未开发说明；维护者身份不显示试用训练可用，也不获得任何私有资料入口。页面隐藏不替代后端鉴权。

## 5. PR 审查问题修复与复测（2026-10-29）

Codex Review 指出：后端已返回登录 200 响应头，但浏览器读取响应正文时抛出原生 `TypeError` 或 `SyntaxError`，原前端仅对 `ApiError` 进入 `me` 核实，可能在服务端已建立会话时仍显示匿名并允许再次提交。该发现经隔离真实 PostgreSQL 与 Chrome 回归复现：新建的测试库 `dt05_verify_80b07fff5f3f4a2b` 中，实际登录 POST 已获 200，测试将该响应的可读正文替换为抛错流；旧代码未发送后续 `me`，断言 `type: login result must be checked with me` 失败。该次失败保留为修复前证据，不记为通过。

修复位于[认证请求](../frontend/src/api/auth.ts)：仅将登录成功响应的 JSON 正文读取失败转换成 `ApiError` 的 `RESULT_UNKNOWN`，交给既有[会话状态](../frontend/src/stores/session.ts)按已提交操作先查询 `me`；不重发登录 POST。若 `me` 仍不能核实，继续显示未知状态。其他失败状态和后端契约未改。

浏览器回归在真实后端完成登录、浏览器接收 Cookie 后，分别让正文读取抛出 `TypeError` 与 `SyntaxError`；逐项断言同一场景仅有 1 次登录 POST、随后至少 1 次 `me`，确认身份后进入工作区并可正常退出。故障为浏览器内可控的正文流注入，不宣称已模拟所有真实网络截断方式。

修复后执行 `frontend/` 下 `npm.cmd run check`，静态、格式、类型及构建全部通过；根目录执行 `& './scripts/Verify-LoginFrontend.ps1'`，新隔离库 `dt05_verify_1dee69bee2024e62` 中 6 项基础测试及 1 项包含上述真实 Chrome 场景的集成测试通过，0 失败/错误/跳过。证据在 `.cache/dt05-test-run.json`、`.cache/dt05_verify_1dee69bee2024e62.log` 和 `backend/target/failsafe-reports/`；日志未命中 `synthetic-`、`SESSION=` 或 `password=`，`git diff --check` 通过。未修改开发库、迁移或后端业务代码；本轮未提交、推送或合并。
