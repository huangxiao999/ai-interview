## 6. 预期账号与 CSRF 等待竞态修复（2026-10-30）

Codex Review 指出：A 的资料操作等待 CSRF 时，另一标签页可切换到 B；旧操作可能带 B 的 token 和 Cookie 写入 B 名下。当前前端在取得 CSRF 后查询服务端身份，校验原操作账号及资料状态代次；写请求携带 `X-Expected-Account-Id`。服务端资料创建、追加与删除在同一短事务取得账号锁、核实当前凭证和权限后比较预期账号，不一致返回 409 `ACCOUNT_CHANGED`，不写入。前端遇到身份变化重新核实，不自动重放原写请求。

新增真实 Chrome 双标签用例：A 填写合成草稿、保存请求停在 CSRF 获取；另一标签退出 A 并登录 B；恢复请求后检查 A 的旧请求未发出资料 POST，B 名下无该正文。新增真实 PG/HTTP 用例：B 会话携带 A 的预期账号提交创建操作返回 409、B 名下无记录；以 B 为预期账号的新操作可成功。两层约束分别覆盖前端已观察到的账号变化及身份查询后仍发生切换的竞态。

## 7. 列表响应乱序修复（2026-10-30）

Code Review 指出，同账号下旧列表请求可以晚于保存或删除后的刷新返回，导致刚保存的简历消失或已删除的简历重新出现在页面。原实现只比较账号状态代次；该代次在同账号写入时不变化。本次在资料 Pinia 状态中增加列表请求序号：每次列表加载取得新序号，保存、删除及原操作结果核实开始时使在途的旧列表结果失效；只有当前账号代次和最新请求序号都匹配，才允许列表成功或失败响应更新页面。此序号只控制页面读取结果，不代替服务端归属和删除屏障。

真实 Chrome 用例在浏览器中先取得并暂停旧列表响应，再分别完成保存、删除及其列表刷新，最后放行旧响应；断言新增简历仍在列表、已删除简历未重新出现。该回归已纳入原有 `ResumeMaterialIT` 浏览器检查。
